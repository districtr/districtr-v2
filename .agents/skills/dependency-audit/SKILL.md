# Dependency audit

This is a survey-and-triage procedure, not an auto-upgrade tool: it enumerates
what's outdated or flagged, and the output is findings to file, not diffs to
apply. Bumping a dependency is a separate, deliberate change — do it one
package at a time, with its own quality-gate run.

## Frontend (Bun)

Bun is the frontend package manager (`app/bun.lock`) and has both checks
built in — no extra tooling needed:

```bash
cd app && bun outdated       # every dependency vs. its latest matching/available version
cd app && bun audit          # known vulnerabilities in installed packages, via the npm advisory DB
```

Both commands run locally, from `app/`, no container required.

## Backend (pip / uv)

`backend/requirements.txt` is a pinned, machine-generated lockfile ("This
file was autogenerated by uv via `uv pip compile ...`" — see its header);
`backend/pyproject.toml` holds only tool config (ruff, coverage), not
dependency declarations. Treat `requirements.txt` as the source of truth for
installed versions.

```bash
docker-compose exec backend pip list --outdated   # installed vs. latest on PyPI
uvx pip-audit -r backend/requirements.txt          # known vulnerabilities, run from repo root
```

`pip list --outdated` needs the container (it reads the installed
environment) — the orchestrator/human runs that one. `pip-audit` reads the
lockfile directly and needs no environment, so it can run on the host via
`uvx` (ephemeral, installs nothing into this checkout).

## Triage

For each outdated or flagged package:

1. **Severity** (for `bun audit` / `pip-audit` findings) — is it a real
   vulnerability class reachable from this app's usage of the package, or a
   dev-only/build-time dependency with no runtime exposure?
2. **Exposure** — does districtr's code path actually exercise the
   vulnerable function/feature, or is the package present but that surface
   unused?
3. **Update cost** — a patch/minor bump is usually low-risk; a major bump
   (especially Next.js — use the separate `next-upgrade` skill for that one,
   it follows the official migration guide — or a core backend package like
   SQLAlchemy/FastAPI) needs its own scoped effort, not a drive-by bump
   alongside unrelated work.

File findings (one issue per package or tightly-related group) rather than
upgrading inline — a dependency bump belongs in its own PR so a regression is
bisectable to that change alone, and so [`quality-gate`](../quality-gate/SKILL.md)
runs against it in isolation.
